# projange

A C++17 / SDL3 port of **Project Angel**, by Impact Studios: made for The
Party IV (Herning, Christmas 1994), final release March 1995. Code
Sigfrid and Walken, art Trajan and Suny, graphics Kej and Mike, music
Clawz, on the Gravis UltraSound.

The demo is a chain of 29 DOS programs, about 21,000 instructions of
16- and 32-bit real-mode code. That is too much to port by hand and keep
exact, so the port is a translation made by a program: the code the
original runs, as an emulation harness traced it, turned into C++
(`src/gen`), on a hand-written model of the machine it runs on. It is
checked against the original frame by frame and GUS write by GUS write.

## Building and running

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j8
./build/projange --data DIR          # DIR: ANGEL.EXE and DRIVERS.VGA [--scale N] [--mute]
ctest --test-dir build               # the port against the original
```

The port needs the demo's own two files, ANGEL.EXE (3,874,636 bytes) and
DRIVERS.VGA (7,400 bytes, with the settings SETUP saved: an S3 card). It
looks for them in `--data DIR`, `$PROJANGE_DATA`, `data/` or next to the
executable.

The demo runs about five minutes and twenty seconds, then the end scroller
loops until Esc, as in the original. Nothing else can be skipped (as the
NFO says). The window shows each mode's picture at 4:3. The music paces
the frames; without an audio device, a timer does.

Headless: `projange --dump DIR --seconds S [--keys F,...] [--wav FILE] [--gus
FILE]` writes `DIR/frames.txt`. Each line holds a frame number, its time, a
CRC-32 of the picture (the bytes the CRTC reads in that frame, then the pel
panning, the overscan colour and the attribute palette) and a CRC-32 of
the DAC. Esc goes down in the middle of the frame before each frame
listed, and up three frames later. `--wav` writes the music, `--gus` the
GUS register writes. `PROJANGE_RAW=f1,f2,...` saves those frames' bytes
and DAC.

## How the demo is built

ANGEL.EXE starts with a 1.5 KB loader; the rest of the file is the
programs and the music. Each program is a chunk: an LZ stream, its
relocations and its entry point. The loader runs them one after the other,
in DOS memory blocks with their own PSPs:

| # | from | what |
|---|---|---|
| 0 | DRIVERS.VGA | video setup: checks the video BIOS against SETUP's CRC; stays as the VGA driver, int FBh (mode 13h; S3 bank and page via CR35 and the start address) |
| 1 | DRIVERS.VGA | the music player: a MOD player for the GUS, int FFh. Its timer is tied to the vertical retrace: it measures the frame with PIT counter 2 and adjusts counter 0 |
| 2 | ANGEL.EXE | XMS stub: 2155 KB of XMS, a GDT and an LDT, 4 GB segments (unreal mode), int FCh |
| 3 | ANGEL.EXE | module loader, int FAh: a chunk of the file to XMS, decrypted with a running CRC-32, then unpacked |
| 4-26 | ANGEL.EXE | the parts: credits, the planet, the Impact logo, flights over landscapes, a space battle, a voxel landscape, the fighters, the canyon, the corridor, the greetings, the angel picture |
| 27 | ANGEL.EXE | the end scroller (mode 10h), until Esc |
| 28 | ANGEL.EXE | the end |

Many parts are "486 code": they go into protected mode only to load a
32-bit code descriptor and 4 GB data limits, and come back to real mode.
They then run 32-bit code in real mode, calling DOS, the player and the
VGA driver from it. They also patch their own code: rotation matrices are
written into the immediates of IMUL instructions, frame counts into
compares, segments into far jumps.

## The translation

`translate.py` (in `../../rea/projange-analisis`) works from what the
harness recorded while the demo ran:
- every basic block with its bytes;
- the control-flow steps;
- every write into code.

Each program becomes one C++ function, entered at a linear address through
a switch. Every block gets a label and every instruction becomes a line or
two of C++ with the original instruction as a comment. Calls are calls of
the function, and an indirect jump goes back to the switch. Immediates and
displacements the program patches are read from memory, where the program
wrote them. Flags are computed only where an instruction that reads them
may follow.

Code the harness never ran is not in the translation. If the port ever
reached it, it would stop and say where. With the same inputs the port
follows the same paths: a run without keys, or with Esc in the scroller.

## Time

As in the harness, the CPU is infinitely fast: running code takes no time,
and time only moves when the program waits:
- **Polling 3DAh:** the third same read jumps to the next retrace edge, or to
  an interrupt due before it.
- **The player's "wait for the next tick" loop:** goes to the next interrupt.

The frames follow the CRTC's registers. An interrupt is taken at the first
point where it can be: the flag set, nothing of its priority in service.
Several interrupt handlers poll the retrace themselves.

## Verification

`ctest` compares two runs with the original under the harness:
- the whole demo, 330 s and 20,183 frames, with all 456,936 GUS register writes and their instants;
- the run with Esc pressed in the end scroller (frame 19,584) through to the demo's exit.

The GF1's synthesis itself has no reference, since the harness logs
registers, not sound.
